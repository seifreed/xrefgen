# Logging and observability

XrefGen runs inside IDA Pro and has no always-on server or external telemetry service. The shared boundary is `modules/observability.py`; application and analysis code emit through its `trace`, `debug`, `info`, `warn`, `error`, or `critical` functions. `modules/presentation/logger.py` remains a backward-compatible import alias.

Events are one JSON object per line with an ISO-8601 UTC timestamp, normalized level, service (`xrefgen`), component, and message. Optional structured fields include `event_name`, `status`, `duration_ms`, and operation-specific counts. ASCII/C1 controls, Unicode line separators, and bidirectional formatting controls are flattened. Common credential assignments, complete authorization/cookie header values, sensitive fields, bearer credentials, URL credentials, and private key blocks are redacted. Do not put binary contents, full request/file contents, secrets, or unnecessary personal data in messages. Exceptions record their type chain and bounded stack frames (file basename, line and function); exception messages, source lines, and absolute paths are omitted.

`general.log_level` accepts `trace`, `debug`, `info`, `warn`, `error`, `fatal`, or `critical`. `general.log_format` accepts `json` (default) or `text`; both formats redact messages and preserve structured context. `general.log_file` optionally enables a UTF-8 rotating file sink. `general.log_max_bytes` defaults to 5 MB and accepts 2–50 MB; `general.log_backup_count` defaults to three and accepts 0–5 backups. On POSIX the file is restricted to owner read/write. Invalid settings warn and use defaults; an unavailable path falls back to stdout, which remains available to IDA's console. If an active file sink fails later, the first failure emits one redacted `logging.sink_failed` warning to the healthy console; repeated failures do not create a log storm. Console sink failures are suppressed so logging cannot interrupt analysis. The console destination remains enabled. Individual text fields are capped at 16,384 characters and events accept at most 64 structured fields. No network destination, external service, or telemetry dependency is required. Python's logging handlers serialize concurrent writes; avoid configuring the logger from worker code.

The remaining core `print` is a user-visible fallback for the statistics dialog when IDA's UI display call fails. Script stdout is reserved for command-line reports, build results, and test summaries.

Use INFO for lifecycle transitions and counts, WARN for recoverable degradation (such as invalid configuration or cache fallback), ERROR for failed operations, and CRITICAL/FATAL only when the plugin cannot continue. DEBUG and TRACE are for opt-in diagnosis. Avoid duplicate exception reports across layers.

Each analysis run creates a random correlation ID and places it, with the `analysis` operation name, in a `ContextVar` scope. Start, finish, and failure events carry stable event names, status, and duration; completion includes result count. Scoped correlation cannot be replaced by event fields, and exception metadata cannot be forged by caller fields. The scope resets on normal return, early return, and exception. Structured event values must be scalar (`str`, integer, finite float, boolean, or null); nested objects are dropped to avoid accidentally logging request, configuration, or other payload data. Configuration validation emits an aggregate count rather than untrusted keys, and artifact/configuration events omit user-selected filenames. The plugin currently has no distributed requests, queues, or background service requiring W3C trace context or OpenTelemetry. Metrics are not generated because there is no persistent service process or monitoring endpoint. For new analysis flows, include relevant module/count/duration fields as structured arguments, never invented trace identifiers. Run `pytest -q tests` for the maintained suite, including structured output, filtering, redaction, propagation, concurrency, rotation, configuration privacy, and sink failure checks.
